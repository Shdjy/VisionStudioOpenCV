# VisionStudioOpenCV 系统优化与智能检测、AI 扩展技术方案

**项目：** VisionStudioOpenCV\
**版本：** V1.1\
**日期：** 2026-11-10\
**技术栈：** C++ / Qt Widgets / OpenCV / CMake / JSON\
**目标：**
在保留现有图像处理平台的基础上，完善算法执行架构，增加目标检测、目标计数、缺陷检测等通用检测能力，并扩展
AI 辅助算法设计与流水线自动生成能力。

------------------------------------------------------------------------

# 1. 建设目标与总体建议

本次改造不是简单增加几个 OpenCV 算子，也不是单纯增加一个 AI
聊天窗口，而是将现有工具逐步升级为一个**可视化图像处理、检测算法构建和
AI 辅助开发平台**。

建议分成三个相互独立、又可以协同工作的子系统：

1.  **图像处理引擎**：负责图像输入、预处理、算子执行、结果传递和代码生成。
2.  **检测算法引擎**：负责目标定位、目标计数、缺陷检测、测量、分类、结果统计和判定。
3.  **AI
    辅助引擎**：负责理解用户需求、分析图像、推荐算法、生成流水线、辅助调参和解释检测结果。

最终支持三种工作方式：

  -------------------------------------------------------------------------------------------------------
  工作模式                使用方式                                           典型用户
  ----------------------- -------------------------------------------------- ----------------------------
  手动构建                用户选择算子、配置参数、组织流程                   熟悉 OpenCV 的开发人员

  检测任务构建            用户选择目标计数、缺陷检测等任务模板，再配置参数   机器视觉工程师

  AI 辅助构建             用户描述目标和检测要求，AI 推荐或生成方案          希望降低算法开发门槛的用户
  -------------------------------------------------------------------------------------------------------

## 1.1 核心建设目标

-   保留现有 Qt Widgets、C++、OpenCV 和算子注册体系。
-   规范算子输入输出、参数元数据和执行结果。
-   建立统一的流水线校验、执行、统计和调试机制。
-   增加通用检测任务模型，不把所有检测逻辑都塞进普通图像算子。
-   支持目标检测、目标计数、缺陷检测、分类、分割和几何测量。
-   支持传统图像处理算法与 YOLO、ONNX 等模型混合使用。
-   支持 AI 根据自然语言和图像生成可校验的算法流程。
-   支持检测结果可视化、规则判定、结果导出和批量测试。

## 1.2 最重要的架构决策

**图像处理算子、检测算法和业务判定规则应分层设计。**

例如"检测图像中有多少个物体"不是一个简单的阈值算子，它通常包含：

``` text
图像输入
  ↓
图像预处理
  ↓
目标定位/分割
  ↓
目标筛选与去重
  ↓
目标计数
  ↓
数量判定
  ↓
结果可视化与导出
```

"检测物体表面缺陷"通常包含：

``` text
图像输入
  ↓
工件定位与 ROI 提取
  ↓
光照/背景校正
  ↓
缺陷候选区域提取
  ↓
缺陷分类或分割
  ↓
面积、长度、位置等特征计算
  ↓
缺陷规则判定
  ↓
OK/NG 输出与结果记录
```

因此，应在现有 PipelineManager
之上增加检测任务层，而不是把目标计数、缺陷检测、OK/NG
判定全部实现为一个超大算子。

# 2. 当前系统基础与需要优先核实的事项

从已检查的项目 README 和部分核心文件来看，项目已有 Qt
Widgets、OpenCV、IOpNode、OpRegistry、PipelineManager、PipelineStep、ProjectManager、JSON
工程和 C++/Python 代码生成等基础。

当前流水线以主流程和分支为主，分支内部通过
`std::vector<std::unique_ptr<PipelineStep>>` 顺序执行；现有
`IOpNode::Process` 采用单输入、单输出的 `cv::Mat` 接口。

这套结构适合当前常规图像处理，但面对检测任务还需要补足以下能力：

  现有基础           需要补足
  ------------------ ----------------------------------------
  算子注册和创建     算子元数据、输入输出类型、参数约束
  单输入单输出处理   结构化检测结果、多个结果字段
  顺序流水线         检测任务编排、分支结果汇总
  参数配置           参数校验、参数分组、单位和枚举
  JSON 工程          检测任务配置、模型配置、标注和评估信息
  图像预览           检测框、掩膜、轮廓、标签和测量结果叠加
  代码生成           检测任务和模型推理代码生成

本方案是基于已检查文件形成的改造设计，不代表已经完成全仓库逐文件审计。正式编码前应先让
Codex 对实际源码、所有算子接口、工程格式和构建依赖做一次完整盘点。

# 3. 总体软件架构

建议采用六层结构：

``` text
┌──────────────────────────────────────────────────────────┐
│                         UI 表现层                         │
│ 图像视图 │ 算子面板 │ 流程编辑 │ 检测配置 │ AI 助手 │ 报告 │
├──────────────────────────────────────────────────────────┤
│                         应用业务层                        │
│ ProjectService │ PipelineService │ DetectionTaskService  │
│ ModelService   │ BatchTestService │ ResultExportService   │
├──────────────────────────────────────────────────────────┤
│                         流程编排层                        │
│ PipelineManager │ PipelineExecutor │ PipelineValidator   │
│ DetectionPlanner│ DetectionExecutor│ TaskValidator       │
├──────────────────────────────────────────────────────────┤
│                         算法能力层                        │
│ OpenCV Operators │ Detection Algorithms │ Model Inference │
│ Filters/Threshold/Contours/Geometry/YOLO/ONNX/Segmentation│
├──────────────────────────────────────────────────────────┤
│                         AI 智能层                          │
│ AI Provider │ Vision Analyzer │ Operator Knowledge Base  │
│ Pipeline Planner │ Generator │ Optimizer │ Result Analyst │
├──────────────────────────────────────────────────────────┤
│                         基础设施层                         │
│ Qt Network │ JSON │ Logger │ Config │ Thread Pool │ Storage│
└──────────────────────────────────────────────────────────┘
```

## 3.1 模块边界

-   UI 只负责交互、显示和用户操作，不直接实现算法。
-   应用业务层负责协调项目、流程、检测任务和批量测试。
-   流程编排层负责节点创建、流程校验、调度和执行。
-   算法能力层提供可复用的图像算子、检测算法和模型推理能力。
-   AI 智能层只负责分析、规划和建议，不绕过本地校验直接执行代码。
-   基础设施层负责网络、配置、日志、线程和文件等通用能力。

# 4. 现有图像处理逻辑优化

## 4.1 算子元数据标准化

现有算子应从"只有名称和参数"升级为可供 UI、校验器和 AI
共同使用的标准描述。

建议增加以下元数据：

``` cpp
enum class DataType
{
    Image,
    GrayImage,
    BinaryImage,
    Mask,
    Contours,
    BoundingBoxes,
    DetectionResults,
    SegmentationMask,
    KeyPoints,
    Measurements,
    Numeric,
    Unknown
};

struct ParameterMetadata
{
    std::string name;
    std::string displayName;
    std::string description;
    std::string type;
    std::string defaultValue;

    bool required = false;
    double minValue = 0.0;
    double maxValue = 0.0;
    double step = 1.0;

    std::string unit;
    std::vector<std::string> enumValues;
};

struct OperatorMetadata
{
    std::string name;
    std::string displayName;
    std::string category;
    std::string description;

    std::vector<DataType> inputTypes;
    std::vector<DataType> outputTypes;
    std::vector<ParameterMetadata> parameters;

    std::vector<std::string> useCases;
    std::vector<std::string> prerequisites;
    std::vector<std::string> limitations;
};
```

正式实现时，还应支持：

-   图像通道要求。
-   图像深度要求。
-   最小/最大图像尺寸。
-   ROI 要求。
-   参数之间的依赖关系。
-   是否支持多线程。
-   是否会修改输入图像。
-   输出对象的语义说明。
-   算子版本号。

所有算子元数据应能导出为 JSON，作为 AI 算子知识库的基础。

## 4.2 不要让所有节点都局限于 cv::Mat

现有 `cv::Mat`
单输入单输出接口对于滤波、阈值、形态学等图像处理算子足够，但检测任务还需要输出框、类别、置信度、掩膜、测量值等结构化数据。

建议采用兼容式扩展：

-   保留现有 `IOpNode::Process`，保证旧算子继续工作。
-   增加统一的 `NodeData` 或 `ProcessingData` 数据容器。
-   新检测节点通过扩展接口传递结构化结果。
-   通过适配器把旧 `cv::Mat` 算子接入新数据流。

概念示例：

``` cpp
struct BoundingBox
{
    cv::Rect2f box;
    int classId = -1;
    float confidence = 0.0f;
    std::string label;
};

struct DetectionResult
{
    std::vector<BoundingBox> objects;
    cv::Mat visualization;
};

struct ProcessingData
{
    cv::Mat image;
    cv::Mat mask;

    std::vector<BoundingBox> detections;
    std::vector<cv::Point> keyPoints;

    nlohmann::json measurements;
    nlohmann::json metadata;
};
```

不要把所有可能的数据都无限堆进一个结构体。实际项目可按图像、检测、测量等数据类型拆分，并通过类型安全的结果对象管理。

## 4.3 增加 PipelineValidator

校验分为四类：

1.  节点校验：算子是否存在、是否能够创建。
2.  参数校验：类型、范围、必填项、枚举值和参数依赖。
3.  数据校验：输入输出类型、通道、深度、尺寸和 ROI 是否兼容。
4.  流程校验：节点顺序、缺失输入、无效连接、循环依赖和执行前置条件。

校验结果应包含错误节点、参数名、错误原因和修复建议。

## 4.4 执行器和结果管理

建议将当前 PipelineManager 的职责拆分：

  模块                      职责
  ------------------------- --------------------------------
  PipelineManager           流程增删改查
  PipelineExecutor          流程执行和调度
  PipelineValidator         执行前校验
  OperatorFactory           算子创建
  ExecutionContext          执行上下文、取消状态和共享资源
  PipelineExecutionResult   执行结果
  PipelineStatistics        执行耗时和资源统计

每个节点至少记录：

-   节点 ID 和算子名称。
-   开始和结束时间。
-   执行耗时。
-   输入图像尺寸、通道和类型。
-   输出数据摘要。
-   成功/失败状态。
-   错误信息。
-   是否使用缓存结果。

应支持单节点调试、从指定节点执行、中间结果预览、取消执行和批量执行。

## 4.5 流程结构演进

V1 保留现有线性流程和分支结构，不急于全面改造成 DAG。

V2 再增加通用节点图：

-   节点 ID。
-   输入输出端口。
-   节点连接关系。
-   拓扑排序。
-   多输入和多输出。
-   分支与汇合。
-   循环依赖检测。
-   中间结果缓存。

# 5. 新增通用检测算法体系

这是本次优化的重点。建议在普通图像处理算子之外，增加"检测任务"概念。

## 5.1 检测任务分类

  检测类型     主要目标                       典型输出
  ------------ ------------------------------ ------------------------
  目标检测     找到图像中的物体               目标框、类别、置信度
  目标计数     统计指定物体数量               总数、分类数量
  缺陷检测     找到工件表面缺陷               缺陷框、掩膜、缺陷类型
  缺陷分类     判断缺陷类别                   类别、置信度
  缺陷分割     获取缺陷精确区域               像素级掩膜
  图像分类     判断整张图像类别               类别和置信度
  实例分割     分离每一个目标实例             每个目标独立掩膜
  几何测量     测量长度、面积、角度等         测量值、单位、公差
  位置检测     获取目标位置和姿态             中心点、旋转角、姿态
  存在性检测   判断目标是否存在               存在/不存在
  完整性检测   判断缺失、破损、装配是否完整   OK/NG 和异常位置

检测任务应由多个可复用节点组成，而不是每种任务都复制一套底层图像处理代码。

# 6. 目标物体检测与计数

## 6.1 目标计数的标准流程

例如：检测一张图像中有多少个瓶盖、零件、药片或其他物体。

建议提供标准任务模板：

``` text
输入图像
   ↓
图像校正/ROI
   ↓
预处理
   ↓
目标提取
   ↓
连通域/轮廓/模型检测
   ↓
目标筛选
   ↓
目标去重
   ↓
目标计数
   ↓
数量判定
   ↓
结果叠加与导出
```

## 6.2 目标提取方式

不要只使用一种算法。根据图像特点提供多种可选方法。

### 方法 A：阈值 + 连通域

适用情况：

-   背景相对简单。
-   目标与背景对比度较高。
-   目标之间存在明显间隔。
-   目标形态相对稳定。

处理步骤：

1.  灰度化或颜色空间转换。
2.  阈值分割。
3.  形态学去噪。
4.  连通域分析。
5.  根据面积、宽高比、圆度筛选。
6.  统计目标数量。

优点：实现简单、速度快、参数可解释。

局限：目标粘连、光照变化、背景复杂时容易误检或漏检。

### 方法 B：轮廓检测

适用情况：

-   目标边界明显。
-   目标之间可以通过轮廓分离。
-   需要同时计算面积、周长和形状特征。

可用特征：

-   面积。
-   周长。
-   外接矩形。
-   最小外接圆。
-   圆度。
-   长宽比。
-   凸包面积。
-   轮廓层级。

### 方法 C：模板匹配

适用情况：

-   目标外观基本固定。
-   目标尺寸和姿态变化较小。
-   背景相对稳定。

需要支持多尺度、旋转搜索和匹配阈值配置。模板匹配不适合外观变化大、遮挡严重或目标形变明显的场景。

### 方法 D：YOLO/ONNX 目标检测

适用情况：

-   目标形态变化较大。
-   背景复杂。
-   存在遮挡或多个类别。
-   传统图像处理难以稳定提取目标。

输出每个目标的：

-   Bounding Box。
-   Class ID。
-   Class Name。
-   Confidence。
-   可选的跟踪 ID。

### 方法 E：实例分割

适用情况：

-   目标粘连。
-   需要精确区分相邻物体。
-   需要计算每个目标的像素面积或轮廓。

可使用实例分割模型，或传统分水岭等方法处理特定场景。

## 6.3 计数逻辑必须独立于目标提取

建议新增 `ObjectCounter`，不要将计数写死在阈值、轮廓或 YOLO 节点中。

配置示例：

``` json
{
  "taskType": "ObjectCounting",
  "targetClasses": ["bottle_cap"],
  "countMode": "PerClass",
  "confidenceThreshold": 0.55,
  "minArea": 100,
  "maxArea": 50000,
  "minWidth": 5,
  "minHeight": 5,
  "deduplicate": true,
  "expectedCount": {
    "min": 10,
    "max": 10
  }
}
```

建议支持：

-   总数量。
-   按类别计数。
-   按 ROI 计数。
-   最小/最大数量判定。
-   目标面积筛选。
-   置信度筛选。
-   重叠框去重。
-   目标粘连处理。
-   计数结果可视化。

计数判定示例：

``` text
检测数量 = 10
期望数量 = 10
判定结果 = OK

检测数量 = 9
期望数量 = 10
判定结果 = NG
原因 = 缺少 1 个目标
```

对于视频或连续图像，不能简单对每帧检测数量求和。需要引入目标跟踪、跨帧去重和计数线逻辑，否则同一个物体会被重复计数。

## 6.4 计数结果结构

``` cpp
struct ObjectCountResult
{
    int totalCount = 0;

    std::map<int, int> classCounts;

    std::vector<BoundingBox> objects;

    bool passed = false;

    std::string message;
};
```

# 7. 工件表面缺陷检测

## 7.1 缺陷检测不是单一算法

缺陷检测应根据缺陷形态、成像条件和数据情况选择不同技术路线。

常见缺陷：

-   划痕。
-   裂纹。
-   凹坑。
-   鼓包。
-   褶皱。
-   污渍。
-   色差。
-   缺料。
-   毛刺。
-   破损。
-   表面异物。
-   印刷缺陷。
-   标签偏移。
-   装配缺失。

建议将缺陷检测拆分为：

1.  工件定位。
2.  ROI 提取。
3.  图像校正。
4.  缺陷候选区域提取。
5.  缺陷分类/分割。
6.  缺陷特征计算。
7.  缺陷规则判定。
8.  检测结果输出。

## 7.2 传统图像处理路线

适用条件：

-   工件位置稳定。
-   光照和相机参数稳定。
-   缺陷与背景有明显灰度、颜色或纹理差异。
-   缺陷类型和形态相对固定。

可组合使用：

  算法                主要用途
  ------------------- ----------------------
  灰度/颜色空间转换   提取亮度或颜色特征
  背景校正            消除光照不均
  高斯/中值滤波       降低噪声
  Top-hat/Black-hat   提取局部亮/暗缺陷
  自适应阈值          处理局部亮度变化
  Canny/Sobel         提取边缘和细线缺陷
  形态学              连接、填补或清除区域
  轮廓分析            提取缺陷区域
  连通域分析          分离缺陷候选区域
  纹理特征            识别纹理异常
  几何特征            判断尺寸、形状和方向

传统方法优势是速度快、可解释、无需训练；不足是对光照、姿态、材料纹理和缺陷变化较敏感。

## 7.3 深度学习路线

### 目标检测

使用 YOLO 等模型定位缺陷，适合：

-   缺陷类型明确。
-   需要缺陷位置和类别。
-   已有一定数量的标注样本。

输出缺陷框、类别和置信度。

### 语义分割/实例分割

适合：

-   缺陷边界不规则。
-   需要精确缺陷面积。
-   需要计算缺陷长度、宽度或占比。
-   缺陷之间需要像素级分离。

### 图像分类

适合只需要判断整张工件图像 OK/NG，或判断缺陷大类的场景。

但分类模型通常不能直接提供精确缺陷位置。

### 无监督/异常检测

适合：

-   正常样本多。
-   缺陷样本少。
-   缺陷类型未知或变化较多。

可以考虑 PatchCore、PaDiM
等异常检测路线。异常检测输出的异常热图仍需阈值化、连通域分析和规则判定，不能把异常分数直接等同于缺陷结论。

## 7.4 缺陷检测配置

建议使用统一任务配置：

``` json
{
  "taskType": "DefectDetection",
  "target": "metal_surface",
  "roi": {
    "x": 100,
    "y": 80,
    "width": 1200,
    "height": 800
  },
  "method": "Hybrid",
  "model": {
    "type": "ONNX",
    "path": "models/defect.onnx",
    "confidenceThreshold": 0.6
  },
  "filters": {
    "minDefectArea": 20,
    "maxDefectArea": 50000
  },
  "rules": [
    {
      "defectClass": "scratch",
      "maxCount": 0,
      "maxArea": 100
    }
  ]
}
```

## 7.5 缺陷特征计算

每个缺陷候选区域建议计算：

-   缺陷类别。
-   置信度或异常分数。
-   外接矩形。
-   面积。
-   周长。
-   最大长度。
-   最大宽度。
-   长宽比。
-   方向角。
-   到工件边缘的距离。
-   所属 ROI。
-   是否超过工艺阈值。

如果要输出毫米、平方毫米等物理单位，必须建立相机标定或像素到物理坐标的换算关系。不能直接把像素数当作实际尺寸。

## 7.6 缺陷判定规则

检测算法负责"找到缺陷"，业务规则负责"是否合格"。

示例：

``` json
{
  "rules": [
    {
      "name": "划痕数量限制",
      "defectClass": "scratch",
      "operator": "<=",
      "value": 0
    },
    {
      "name": "凹坑面积限制",
      "defectClass": "dent",
      "operator": "<=",
      "value": 100
    },
    {
      "name": "裂纹长度限制",
      "defectClass": "crack",
      "operator": "<=",
      "value": 2.0,
      "unit": "mm"
    }
  ]
}
```

最终输出：

-   OK/NG。
-   缺陷数量。
-   缺陷类别统计。
-   缺陷位置。
-   缺陷尺寸。
-   触发的判定规则。
-   判定原因。

规则配置必须支持版本管理，并保存实际使用的规则版本，便于追溯。

# 9. 检测任务统一数据模型

建议增加 DetectionTask、DetectionResult 和 InspectionDecision。

## 9.1 任务定义

``` cpp
enum class DetectionTaskType
{
    ObjectDetection,
    ObjectCounting,
    DefectDetection,
    DefectClassification,
    Segmentation,
    ImageClassification,
    GeometryMeasurement,
    PresenceCheck,
    CompletenessCheck
};

struct DetectionTask
{
    std::string id;
    std::string name;

    DetectionTaskType type;

    nlohmann::json configuration;
};
```

## 9.2 检测结果

``` cpp
struct DefectInfo
{
    std::string defectType;
    float confidence = 0.0f;

    cv::Rect boundingBox;
    cv::Mat mask;

    double area = 0.0;
    double length = 0.0;
    double width = 0.0;
};

struct DetectionResult
{
    std::vector<BoundingBox> objects;
    std::vector<DefectInfo> defects;

    int objectCount = 0;
    int defectCount = 0;

    cv::Mat visualization;

    nlohmann::json measurements;
    nlohmann::json statistics;
};
```

正式实现时，`cv::Mat mask`
的生命周期和内存占用必须明确；大量批量检测场景应考虑共享数据或按需保存掩膜。

## 9.3 最终判定

``` cpp
enum class InspectionStatus
{
    Unknown,
    Pass,
    Fail,
    Error
};

struct InspectionDecision
{
    InspectionStatus status = InspectionStatus::Unknown;

    std::vector<std::string> reasons;

    nlohmann::json ruleResults;
};
```

检测结果和最终判定必须分开：

-   检测结果表示算法发现了什么。
-   判定结果表示这些发现是否满足业务规则。

这样可以复用同一个检测算法到不同产品、不同工艺标准中。

# 10. AI 扩展模块设计

## 10.1 AI 的职责边界

AI 应负责：

-   理解用户描述。
-   分析图像内容。
-   判断适合哪类检测任务。
-   检索现有算子和检测能力。
-   推荐传统算法或深度学习路线。
-   生成结构化任务配置。
-   生成流水线。
-   根据运行结果提出优化建议。
-   解释检测结果。

AI 不应：

-   直接执行任意 C++ 代码。
-   绕过算子注册表创建未知算子。
-   绕过 PipelineValidator。
-   未经用户确认覆盖正式工程。
-   把模型的主观视觉判断当作精确测量结果。
-   自行宣称检测算法达到某个准确率。

## 10.2 模型配置

配置字段：

  字段            说明
  --------------- ------------------
  Name            配置名称
  Provider        服务商
  BaseUrl         API 地址
  ApiKey          API Key
  Model           模型名称
  ApiType         API 协议类型
  Temperature     随机性参数
  MaxTokens       最大输出长度
  Timeout         超时时间
  VisionEnabled   是否支持图像输入
  Enabled         是否启用

第一阶段优先支持 OpenAI-compatible API，通过 Provider 适配不同服务商。

Qt 项目建议使用 Qt Network
异步请求，支持超时、取消、错误处理和日志脱敏。API Key 在 Windows
上优先使用 DPAPI 保护，不写入普通工程文件。

## 10.3 AI 业务模块

建议新增：

  模块                       职责
  -------------------------- ---------------------
  IAiProvider                AI 服务统一接口
  OpenAiCompatibleProvider   OpenAI 兼容接口实现
  AiConfigManager            模型和密钥配置
  VisionAnalyzer             图像理解和场景分析
  RequirementParser          用户需求结构化
  OperatorKnowledgeBase      算子知识库
  DetectionKnowledgeBase     检测任务知识库
  PipelinePlanner            流程规划
  PipelineGenerator          流程生成
  DetectionTaskGenerator     检测任务配置生成
  AiResponseValidator        AI 输出结构校验
  PipelineOptimizer          算法优化建议
  ResultAnalyzer             检测结果分析

## 10.4 AI 生成检测任务的示例

用户输入：

"统计图片中的瓶盖数量，如果数量不是 12 个就判定 NG。"

AI 应先识别这是 `ObjectCounting` 任务，再根据图像情况推荐：

-   简单背景：阈值 + 连通域。
-   目标边界清晰：轮廓 + 几何筛选。
-   背景复杂或遮挡：YOLO 检测。
-   目标粘连：实例分割或分水岭等方法。

然后生成任务配置：

``` json
{
  "taskType": "ObjectCounting",
  "targetClass": "bottle_cap",
  "method": "ConnectedComponents",
  "preprocess": [
    {
      "operator": "Gray"
    },
    {
      "operator": "Threshold",
      "parameters": {
        "threshold": 120
      }
    }
  ],
  "countRule": {
    "expectedCount": 12,
    "operator": "=="
  }
}
```

以上仅为结构示例。AI
必须根据真实算子元数据生成参数；若图像条件不适合连通域方法，应给出其他方案或要求用户补充信息。

## 10.5 AI 生成缺陷检测方案

用户输入：

"检测金属表面的划痕和凹坑，统计数量和面积，超过标准判定 NG。"

AI 应输出：

1.  图像成像条件分析。
2.  工件定位和 ROI 建议。
3.  推荐传统算法、深度学习或混合方案。
4.  缺陷类别定义。
5.  缺陷区域提取方案。
6.  面积、长度等测量方式。
7.  判定规则。
8.  需要的训练数据或标注建议。
9.  不确定性和风险提示。

如果用户没有提供足够的样本、标注或成像条件，AI
应明确指出不能保证检测效果，而不是直接生成一个看似完整但未经验证的算法。

# 11. AI 自动生成与执行闭环

统一流程：

``` text
用户图像 + 自然语言需求
          ↓
AI 视觉分析
          ↓
需求结构化
          ↓
确定检测任务类型
          ↓
检索算子/检测能力
          ↓
生成任务方案
          ↓
生成结构化 JSON
          ↓
JSON Schema 校验
          ↓
算子与参数校验
          ↓
输入输出兼容校验
          ↓
创建临时任务
          ↓
执行检测
          ↓
结果可视化和指标统计
          ↓
用户确认或提出修改
          ↓
AI 优化并重新执行
          ↓
保存工程和检测记录
```

必须具备以下保护：

-   生成结果只进入临时任务。
-   所有节点通过本地注册表创建。
-   不存在的算子必须拒绝。
-   不合法参数必须拒绝或在明确规则下修正。
-   执行前必须完成校验。
-   用户确认后才能应用到正式工程。
-   保留原始配置和修改记录。

# 18. 测试数据和算法评价体系

检测系统不能只通过"界面上能显示结果"判断完成。必须准备测试图像和真实标签。

## 18.1 目标计数评价

建议统计：

-   Count Error：预测数量与真实数量的差值。
-   MAE：平均绝对计数误差。
-   Precision/Recall：目标检测匹配指标。
-   漏检数量。
-   误检数量。
-   单张图像耗时。

## 18.2 缺陷检测评价

建议统计：

-   缺陷级 Precision。
-   缺陷级 Recall。
-   F1。
-   漏检率。
-   误报率。
-   缺陷定位 IoU。
-   分割 Dice/IoU。
-   不同缺陷类别的单独指标。

必须区分图像级、目标级和像素级指标，不能混为一个准确率。

## 18.3 数据集管理

建议增加测试集目录规范：

``` text
dataset/
├── object_counting/
│   ├── images/
│   └── annotations/
│
├── defect_detection/
│   ├── images/
│   ├── labels/
│   └── masks/
│
└── evaluation/
    ├── test_cases.json
    └── evaluation_report.json
```

数据标注可先使用外部工具完成，后续再考虑集成标注功能。

## 18.4 工业检测的关键注意事项

-   测试集应覆盖正常和异常情况。
-   应覆盖不同光照、位置、姿态和批次。
-   训练集和测试集不能简单随机拆分导致同一工件泄漏。
-   对漏检和误报分别统计。
-   关键缺陷应按风险等级设定不同阈值。
-   模型置信度阈值必须通过验证集确定。
-   生产部署前需要进行连续运行和稳定性测试。

# 21. 最终结论

建议将 VisionStudioOpenCV 从单纯的 OpenCV
算子流程工具，升级为具备通用检测任务能力的视觉算法平台。

最关键的不是增加多少算子，而是建立清晰的三层能力：

1.  **图像处理层**：负责预处理、分割、滤波、轮廓、几何等基础算法。
2.  **检测任务层**：负责目标检测、目标计数、缺陷检测、测量和 OK/NG
    判定。
3.  **AI
    辅助层**：负责需求理解、算法规划、任务生成、参数建议和结果分析。

其中：

-   目标计数应采用"目标提取 + 筛选去重 + 计数 + 规则判定"的通用流程。
-   缺陷检测应采用"工件定位 + ROI + 缺陷提取/模型推理 + 特征计算 +
    规则判定"的通用流程。
-   AI 应生成结构化任务配置和流水线，不应直接生成并执行任意代码。
-   传统 OpenCV 与深度学习应作为可组合的算法能力，而不是互相替代。
-   检测结果与 OK/NG 业务判定必须分离。
-   所有检测算法都应通过真实测试集验证，尤其要单独关注漏检率和误报率。

**最终方向：以 OpenCV 为基础算法引擎，以检测任务框架为业务核心，以
ONNX/YOLO 等模型扩展算法边界，以 AI 实现自然语言驱动的视觉算法构建。**

# 附录 B：建议优先落地的两个示范任务

## 示例一：目标数量检测

**需求：** 检测图像中瓶盖数量，要求数量为 12 个，否则 NG。

V1 实现路线：

-   简单背景：灰度/颜色分割 + 形态学 + 连通域。
-   复杂背景：YOLO 检测 + NMS。
-   目标粘连：实例分割或分水岭。
-   输出：目标框、数量、置信度、数量判定和叠加图。

## 示例二：金属表面缺陷检测

**需求：** 检测划痕和凹坑，统计数量和面积，超过工艺阈值判定 NG。

V1 实现路线：

-   固定成像条件：背景校正 + 滤波 + 局部阈值/形态学 + 连通域。
-   缺陷形态复杂：YOLO 检测或分割模型。
-   缺陷样本不足：评估基于正常样本的异常检测。
-   输出：缺陷位置、类别、面积、长度、数量、规则判定和叠加图。

这两个示范任务应作为检测任务框架的首批端到端验收用例。
